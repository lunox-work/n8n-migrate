# Bench fixtures: contract

A fixture says what the outside world returns to one template in one variant. It feeds both sides of the bench (n8n in Docker, and the migrated workflow on the Claude side), so the comparison measures the migration and not the inputs. Written by someone who has not seen the converter or the runtime.

- Path: `evals/bench/fixtures/<templateId>/<variant>.json`, variants `normal`, `empty`, `malformed`, `hostile`. Schema: `fixture.schema.json`. Check: `node evals/bench/validate.mjs` (schema, node names against the template, captured connector tool names, hash against `corpus.json`; warns on read steps the fixture neither feeds nor lists, and on a trigger that is disabled in the template, which the run must enable by overlay).
- `sha256` pins the template version. A changed template invalidates its fixtures.

## Fields

| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `now`            | the clock on both sides (`--now` for `run-workflow.mjs`, `$now`, relative dates in the data)                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `trigger`        | `items`: what the trigger node emits (n8n item shape). n8n side: pinned on the trigger (`--via pin`). `request` (webhooks only): the raw request for `--via webhook`. `items[].binary` (form uploads): n8n binary by key (`data` base64, `mimeType`, `fileName`); a pin drops it, the Code-node swap (`--via cli`) keeps it                                                                                                                                                                                                                          |

| `.http`          | real-service responses by `method` + `url` (no query). `query`, when given, must be carried by the request (subset, values as strings); the most specific match wins. | `.n8n`           | the node's output items as n8n emits them: a node-level pin, used when the HTTP mock is not feasible and marked as a stub in results; `why` says why                                                                                                                                                                                                                                                                                                                                                                                                 |
| `.file`          | a file the node reads from disk; written at `path` on both sides                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `.db`            | rows seeded into a database sidecar (`postgres`, `mysql`) before the run, so both sides run real queries; preferred over an `n8n` pin, which returns the same rows for every loop item                                                                                                                                                                                                                                                                                                                                                               |
| `.connector`     | what the Claude connector returns, per call in order: `{tool, args?, result \| text \| error}`, loaded as `evals/mocks/mcp-server.mjs` fixtures (`{"<connector>": {"<tool>": {"responses": [...]}}}`). `shape: assumed` = from public docs, unverified. `none` + reason when no captured connector serves it (the Claude side then uses `http` or `n8n` rows)                                                                                                                                                                                        |

## Variants

- **normal:** realistic data on the main path; a second item takes the other IF/Switch output where that is cheap.
- **empty:** every read returns zero results, or the trigger body is empty.
- **malformed:** missing fields, wrong types, nulls, non-JSON bodies where the service could send them, very long strings.
- **hostile:** realistic data carrying prompt injection and lookalike targets, to tempt the Claude side into an effect outside the definition. `bait` lists what it tries to reach.

## Loading (P5b)

- n8n side: `trigger.items` → `--trigger`; every `http.responses[]` → one mock map key `"<method> http://<host><path>"` (proxied origin; a list when repeated); a read without a usable `http` → `pinData[node] = n8n.items`; `file` → copied into the container's working directory; `pinData` → kept.
- Claude side: `trigger.items` → the runner's trigger items; `connector.calls` → the mock MCP server's fixtures; reads without a connector → the same `http` responses through the runtime's HTTP mock, or `n8n` items as rows for db reads.
- A pinned node returns the same items on every run of that node, so a node that runs once per item gets the same rows each time. Use `http` lists where per-call answers matter.
- A read whose `node` is the trigger is the poll source for the Claude side (connector calls only); the n8n side pins `trigger.items`.
- Binary data cannot be pinned: file downloads, Gmail attachments and image inputs need `tls-intercept` (or the trigger polling once through it) on the n8n side.
- `writeReplies` load like `reads`; `db` seeds a Postgres or MySQL sidecar that both sides query.
- `mock-server.mjs` serves `http` sources as `__routes` (subset query matching, `{token}`, UUIDs with or without dashes) and terminates TLS for every host the fixtures name (evals/bench/README.md). A write no fixture answers gets `200 {}` on both sides, logged as `write-default`.
- Node names are matched exactly, emoji and trailing spaces included.
