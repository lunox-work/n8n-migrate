## P1. Fixture connector rows and n8n-side rows disagree on what the service returns (4722, 2415)

- **Evidence, 4722 (Gmail `get`, `simple: false`).** The n8n side reads `GET /gmail/v1/users/me/messages/<id>?format=raw`; the raw message in the fixture carries `Message-ID`, `List-Unsubscribe`, `Precedence` (first mail) and `In-Reply-To`, `References` (second). The Claude side's `get_message` rows (`shape: assumed`) carry no headers at all. The template's agent prompt prints `headers['list-unsubscribe']`, `headers.precedence`, `headers['in-reply-to']`, `headers.references`, so the replayed model input can never match, whatever the converter does. After iteration 1 this is 4722's only blocker (bench `p6-i1`, gate 4 detail: `List-Unsubscribe Header:` empty on the Claude side).
- **Evidence, 2415 (Notion `database:get`, `simple: false`).** The n8n pin is a REST database object with property ids (`%3AbQr`, `Zx%7Bp`, …) and option ids and colours; the `notion-fetch` text row's `<data-source-state>` schema has neither. The template's agent prompt embeds `inputDatabase.properties` with `id` per property, so once the ReAct agent is modelled the prompt will differ on the ids alone. Confirmed in `p6-i7`: with the ReAct prompt built as n8n builds it, the property ids are 2415's only gate-4 difference.
- **Proposed change.** Check the real output of Gmail `get_message` (with `messageFormat: FULL_CONTENT`) and Notion `notion-fetch` on a database, once reading real data is allowed. Where the real connector returns headers or property ids, add them to the fixture's `connector` rows so both sides are fed the same facts. Where it does not, keep the rows and mark the template's gate 4 as `connector-limited` in the fixture's `expect.offline`, so the gap is reported as a connector limit rather than a migration failure.
- **Why not in the loop.** It changes fixtures, and which way it goes depends on real connector output nobody has captured.

## P2. Gate 8 in an in-process run is reported as a bench defect

- **Evidence.** `p6-i2` and `p6-i3`: 2777 passes gates 3–7 in process and stops at gate 8 with `bench defect: no claude-driver measurement for this template`; the same commit under `--driver claude` (`p6-i2c`, 2 `claude -p` runs) passes gate 8.
- **Proposed change.** Either document in `evals/bench/README.md` that the loop re-runs `--driver claude` on every template that reaches gate 8 in process (2 runs each), or let `run.mjs` do that automatically within the claude budget. The gate itself stays as it is.
- **Why not in the loop.** It changes how the bench reports a gate.

## P3. The comparer reads n8n's multipart bodies as raw text (2167)

- **Evidence.** `p6-base30`: 2167 stops at gate 4, `flaky model step: model-written fields differ in replay`. n8n's Post Discussions body (HTTP Request, `multipart-form-data`) is logged by `mock-server.mjs` `decodeBody()` as one string with the boundary and every part; the Claude side's body is the field object (`body`, `position[old_path]`, …, `position[new_line]: 48`). The model-written `body` text is the same on both sides; only the encoding differs, and `new_line`/`old_line` are strings in a form part and numbers on the Claude side.
- **Proposed change.** Decode `multipart/form-data` in the mock log into `{field: value}` (files as `{filename, contentType, size, sha256}`) and compare form fields as strings.
- **Why not applied here.** It changes the comparer, which was not among the approved bench changes.
- **Status: applied** (approved 2026-11-14). `mock-server.mjs` `parseMultipart()`; `compare.mjs` `formStrings()` on both sides when the body is a form.

## P4. n8n's clock and timezone differ from the Claude side's (1953, 6270)

- **Evidence.** `p6-base30`: 1953 and 6270 stop at gate 4 on the agent's prompt, whose `$now` renders `2026-11-14T04:55:48.679Z` on n8n and `2026-11-13T23:55:40.374-05:00` on the Claude side. Two causes: the bench's n8n runs with `GENERIC_TIMEZONE=UTC` (`evals/n8n/container.mjs`) while the runtime takes n8n's default `America/New_York` for a template without a timezone (`runtime/src/engine.mjs` DEFAULT_TIMEZONE); and n8n's `$now` is the container's wall clock (8 s after the run started in 1953, after two live model calls) while the Claude side's clock is virtual from n8n's `startedAt`.
- **Proposed change.** Run the bench's n8n with n8n's default timezone (`America/New_York`, and `scheduleItem()` with it), re-recording the templates whose prompts carry dates; and either freeze n8n's clock (libfaketime in the image) or compare `$now`-derived text up to the timezone-normalised minute.
- **Why not applied here.** It changes every baseline recording and the environment, beyond the approved changes.
- **Status: applied** (approved 2026-11-14, without freezing n8n's clock). n8n runs with `GENERIC_TIMEZONE` and `TZ` `America/New_York`; `scheduleItem()` takes the zone; `compare.mjs` `maskRunTime()` masks timestamps within ±10 minutes of n8n's `startedAt` in write fields, the reply and replayed model inputs that differ only by them (digits only; shape and offset kept). Re-recorded: 1953 and 6270 (their model requests carried `$now` rendered in UTC).

## P5. Gate 8 cannot be measured for folders with `http` steps (3102, 2413)

- **Evidence.** `p6-base30`: 3102 and 2413 pass gates 3–7 in process; the claude driver does not run folders with `http` steps (`claude-driver.mjs`), so gate 8 stays `bench defect: no claude-driver measurement … the folder has http steps`.
- **Proposed change.** Route the task driver's `http` through the bench mock (the runner's HTTP host pointed at the mock, as the in-process driver does), so the claude driver can run these folders.
- **Why not applied here.** It changes the claude driver, beyond the approved P2.
- **Status: applied** (approved 2026-11-14). `http-preload.mjs`, preloaded with `NODE_OPTIONS --import` into the session's `runtime/runner.mjs` processes only (the Claude Code binary ignores `NODE_OPTIONS`), sends the runner's `fetch` to a host `mock-server.mjs` holding the fixture's http routes; dummy `N2C_SECRET_<NAME>` per declared secret.

## P6. Writes with the same target are paired by order, not by content (2167)

- **Evidence.** `p6-base30c`: 2167 stops at gate 4, `field map: different fields`. Both sides post the same two GitLab discussions to the same merge request (one per changed file, `position[new_path]` `src/invoice.ts` and `test/invoice.test.ts`, bodies and positions equal). n8n's HTTP Request node sends the two items concurrently, so the mock logged the test-file post first; the runner sends them in item order. `compare()` pairs same-key writes in list order, so each n8n post is compared with the other file's post and both pairs differ.
- **Proposed change.** Among unused Claude writes with the same `service.action.target`, pair an n8n write first with one whose fields all match (`sameField`, run-time masking included), and only then fall back to list order for the field diff. Order stays reported (`sameOrder`).
- **Why not applied here.** It changes the comparer beyond the approved P3–P5.
- **Status: applied** (approved 2026-11-14, commit 5269638). `compare.mjs` `pairWrites()`: within one `service.action.target`, a maximum-weight assignment (Hungarian method, integer weights) on the number of equal fields (run-time masking included; a differing object field counts its share of equal top-level keys), ties to the pairing closest to list order. `sameOrder` is still reported, not gated.

## P7. A Sheets `values` fixture holds a JSON `null` cell that the real API never sends (2063 malformed)

- **Evidence.** `p6-i5`: 2063 stops at gate 5, malformed: n8n updates `Add your search here!B3`, the Claude side `!B2`. The malformed fixture's `http` source for "Google Sheets - Get searches to scrap" returns row 2 as `[url, null]`; its `connector` source (the CSV export) has an empty cell there. n8n's `lookupValues` compares `null?.toString()` (undefined) with the filter value `""`, so it skips row 2 and takes row 3; with an empty cell it would take row 2, as the Claude side does. The Sheets API `values.get` leaves trailing empty cells out of a row and never writes `null`.
- **Proposed change.** Write row 2 of that response as `[url]` (or `[url, ""]`), so the http and connector sources state the same sheet.
- **Why not in the loop.** It changes a fixture.
- **Status: applied** (approved 2026-11-14, commit c7b8dc1). Row 2 is `[url]` in the read and in both update look-ups of the malformed fixture.

## P8. The claude driver's http preload reuses keep-alive sockets the host mock has closed (2063)

- **Evidence.** `p6-full30`: 2063 passes gates 3–7 in process (after P7) and stops at gate 3 under the claude driver, `runner bug: step Update Status to Error: socket hang up` (normal) and `ECONNRESET` (hostile). The runner's event log (`.work/claude-driver/p6-full30-2063-normal/.../.n2c/events.jsonl`) shows each http request followed by a ~6 s replay of the run before the next one (`resumed`), and an exact alternation: q2 SerpApi ok (fresh socket); 6.3 s later q3 fails; q4, on a new socket, ok; 6.4 s later q5 fails. `http-preload.mjs` sends through `node:http` `request()` with the default global agent, which keeps sockets alive (Node 19+); the host mock (`createServer`, default 5 s `keepAliveTimeout`) closes an idle socket after 5 s, and the runner, busy replaying for 6 s, writes the next request on the closed socket before it handles the close. The host mock logs only the requests that got through; the in-process driver has no sockets and passes the same steps.
- **Proposed change.** In `http-preload.mjs`, send each request on its own connection (`agent: false`), or give the host mock a `keepAliveTimeout` longer than the claude driver's timeout. Either keeps the bench from failing a step on a transport race of its own making.
- **Why not applied here.** It changes the claude driver beyond the approved P6 and P7. Whether the runner itself should retry an idempotent request on a stale connection (undici, used outside the bench, has the same race when the runner blocks for longer than a server's keep-alive) is a separate runner question, kept out of the bench decision.
- **Status: applied** (approved 2026-11-14). `http-preload.mjs` sends each request with `agent: false` and `Connection: close`. `p6-a1`: 2063's claude driver runs to `done` on normal and hostile with every http request answered (no `socket hang up`/`ECONNRESET`); it now stops at gate 4 on a runner bug the transport error hid (LOOP.md, Stage A).

## P9. The in-process host records a runner file part as a JSON object, not as the mock's file part (no dev template yet)

- **Evidence.** Iteration 8 lets an HTTP Request `multipart-form-data` body carry file parts from binary (`{$file: {fileName, mimeType, data}}` in the runner's request, `nodes2.mjs` `multipartPairs`). The claude driver's host mock decodes the bytes `executeHttp` sends into `{filename, contentType, size, sha256}`, as it does for n8n (P3). The in-process host (`claude-side.mjs` `host.http`) passes the runner's request body to `fromHttp` as it is, so `formStrings()` would turn the file part into its JSON text and the comparer would report a different field where both sides sent the same file. No reached step in the 30 dev fixture templates has a binary form field (1900, 3669 and 3102 have one, on steps blocked or not reached), so no verdict depends on it today.
- **Proposed change.** In the in-process host, map a `$file` part to `{filename, contentType, size, sha256}` of its decoded bytes before the body is recorded, as the mock does for a real multipart body.
- **Why not applied here.** It changes the bench's Claude-side recording, which is frozen.
- **Status: applied** (approved 2026-11-14). `claude-side.mjs` `decodeFileParts()`: for a `multipart-form-data` request the in-process host records each `$file` part as `{filename (basename), contentType (before any `;`), size, sha256}` of its decoded bytes, with no defaults, and matches routes on that body; text fields are left for `formStrings()`. A test checks it equals `parseMultipart()` of `multipartBody()`'s bytes. No dev template reaches such a step, so no verdict moves (`p6-a1`).

## P10. The comparer cannot pair a Gmail `reply` tool call with n8n's REST send of the reply (1953)

- **Evidence.** `p6-i9` (after iteration 9): 1953's replayed model inputs all match n8n's; gate 4 fails with `bench defect: effects the comparer table does not cover`. `cmp.writes`: missing `gmail.send:marco.bellini@harbourline.example` (n8n's Send reply, Gmail `reply` over REST: `GET messages/<id>?format=metadata`, `GET profile`, `POST messages/send` with `to`, `subject`, `thread` and a quoted-printable MIME body with `=\r\n` soft line breaks); extra `gmail.send:` (the Claude side's `gmail.reply` tool call, `{messageId, htmlBody}`, whose table row has no target and only `body`). The body text is the same once the soft line breaks are decoded; the recipient, subject and thread follow from the message being replied to, which the Claude call names by `messageId`.
- **Proposed change.** In `effects.json`/`compare.mjs`: decode a quoted-printable MIME body before comparing (`Content-Transfer-Encoding: quoted-printable`), and give the `gmail.reply` row a target and fields resolved from the replied-to message as the fixture serves it (its `From` as `to`, `Re:` subject rules as n8n's reply builds them, `threadId` as `thread`), or compare a reply on `{thread, body}` on both sides. The comparer's table stays its own, written from Gmail's REST docs and the connector schema, never from the converter's map.
- **Why not in the loop.** It changes the comparer.
- **Status: applied** (approved 2026-11-14, release point 1). `compare.mjs`: `parseMime()` decodes the body by its transfer encoding (the part's, else the message's; quoted-printable per RFC 2045 6.7); `refsOf(fx)` indexes the Gmail messages the fixture serves (REST resources, connector rows, thread lists, n8n items, the profile's address) and `replyFields()` resolves a reply's thread, recipients (Reply-To, else From; reply-all adds To and Cc without the account's address, RFC 5322 3.6.3) and subject; the `gmail.reply` row in `effects.json` has `replyTo: args.messageId`, a target and `to`, `cc`, `subject` (`cmp: subject`, leading `Re:`/`Fw:` dropped), `body`, `thread`, written from Gmail's threading guide and REST docs.

## P11. Connector rows are single-use, so a second read of the same id gets another row (4722)

- **Evidence.** `p6-i9`: 4722's Gmail Trigger now reads each new message again with `get_message`, as n8n's trigger does (iteration 9). The fixture's `get_message` rows were written for the downstream Gmail `get` node only (n8n's trigger is pinned, so n8n makes no such call). `pickConnector()` gives the trigger's two detail calls the two rows (args match), marks them used, and the later Gmail `get` for the first message, finding no unused row, gets the last row: the second message (Priya's). The agent prompt then names the wrong sender (gate 4 detail moves from the `List-Unsubscribe` header of P1 to `priya@acme-logistics.example` vs `info@coresignal.example`; same gate and cause). A real connector returns the same message for the same id each time.
- **Proposed change.** In `pickConnector()`: when no unused row matches the call's args, reuse a used row whose args match before falling back to the node's rows or list order (a read with the same arguments answers the same). Writes keep their single-use order.
- **Why not in the loop.** It changes how the bench answers connector calls.
- **Status: applied** (approved 2026-11-14, release point 1). `claude-side.mjs` `pickConnector()`: unused row whose args fit, then (a read, by `effects.json`) a used row whose args fit, then the step's own rows, then any; reads keep a used-set per tool and calling step, writes one per tool. The claude driver passes each row's `args` and `reuse` for reads to `mcp-server.mjs`, which matches the same way.

## P12. A live n8n recording fails when the model shim waits on the memory gate (1900)

- **Evidence.** `p6-i10` and `p6-i10r` (iteration 10, LOOP.md): 1900 needed its first live n8n recording (eight model nodes). With the bench's n8n container up, free memory stayed at 33–39%; `claude.mjs` `memoryGate()` wants 40% while the container runs and waits in 3-minute steps, so the shim held n8n's model request for minutes and n8n aborted it ("The connection was aborted, perhaps the server is offline", on `ChatGPT-ex4`, then `ChatGPT-ex3.2`). The run was saved as the template's recording with `status: error`, so later runs would have replayed a failed baseline (the file was deleted by hand). Gate 3 then reads `fixture: n8n baseline failed`, a verdict about the machine, not the template.
- **Proposed change.** Check memory once before a live-recorded n8n run starts (enough headroom for its model calls), not per call in the middle of it; and never save a recording whose run failed because the shim did not answer (mark the row `bench defect: recording interrupted` instead). Optionally run the live recording with the container's model requests on a longer timeout.
- **Why not in the loop.** It changes the bench's environment handling and the recordings.
- **Status: applied** (approved 2026-11-14, release point 1). `run.mjs` `n8nRun()`: a run with model nodes checks memory once before it starts (`memoryGate({need: 25})`, CLAUDE.md's floor: the recording is one sequential job) and marks the shim session `memoryChecked`, so `claudeP()` skips the per-call gate for its model calls; `n8n-side.mjs` `recordingInterrupted()` (a shim error, or a model node or its root failing on a transport error) stops the template with `recording interrupted (…, not saved)` before the recording is written. A model node failing on what the model answered stays a baseline.

## P13. The stand-in model sometimes returns its answer envelope as the reply text

- **Evidence.** Release point 1 (`evals/bench/RELEASE-1.md`, held-out runs, which the loop does not read): `claude -p` answers through `ANSWER_SCHEMA` (`{type, text}`), and haiku sometimes writes that envelope as a JSON string inside `text`, so the provider reply n8n receives is `{"type":"text","text":"…"}`. In one run it also dropped a wrapper level of n8n's structured-output schema, and n8n's own parser failed the baseline (bucket `fixture`). Replays then carry the envelope to the Claude side.
- **Proposed change.** In `liveAnswer()`, when the answer's text is itself a JSON object of the envelope's shape, unwrap it (repeat while it nests). Do not re-draw a reply because n8n rejected it: that would select baselines.
- **Why not in the loop.** It changes the bench's model shim and the recordings it writes.
- **Status: applied** (approved 2026-11-15, commit 6cedef7). `model-shim.mjs` `envelopeOf()`/`modelAnswer()`: the whole text one JSON object with only the envelope's keys and a valid `type` is unwrapped, again while it nests (a `tool_use` envelope becomes tool calls); cached draws get the same unwrap; a `text` that is an object is kept as its JSON text (it was `String()`ed to `[object Object]`). Recordings that carried an envelope (5035, every variant; 2703 hostile) were moved to `.work/recordings-pre-p13/` and re-record on next use. The structured-output wrapper drop is not a shim defect: the draw itself (2271 normal) omits the `__structured__output__object` level the prompt's schema asks for, and the shim forwarded it intact; the baseline stays failed (bucket `fixture`), not re-drawn.

## P14. A prompt with a NUL byte cannot be passed to `claude -p` as an argument

- **Evidence.** Release point 1 (RELEASE-1.md): a malformed fixture's chat text holds a NUL byte; `claudeP()` passes the prompt in argv, Node refuses (`must be a string without null bytes`), the shim answers with an error, and P12 stops the template as `recording interrupted` (nothing saved).
- **Proposed change.** Send the prompt on stdin (`claude -p` reads it there) for every bench `claude -p`.
- **Why not in the loop.** It changes how the bench calls the model.
- **Status: applied** (approved 2026-11-15, commit aab3800). `claude.mjs` `spawnWithPrompt()` writes the prompt to stdin and `claudeArgv()` carries none, for the model shim, the judge, the headless skill run and the claude driver.

## P15. Replayed agent turns are not checked against the tools the Claude side ran

- **Evidence.** `sameModelInput()` compares the Claude request's system and user text with n8n's recorded request; tool results in the transcript are not compared, and reads are reported, not gated. With n8n's replies replayed, an agent on the Claude side that never ran a read tool (the tool blocked or missing) still gets n8n's next turn and its final answer, and the template passes. Dev 6270 (`rel1-dev`) passes with a read only n8n made (`feeds.bbci.co.uk … rss.xml`); release point 1 found a held-out pass of the same kind.
- **Proposed change.** For each replayed agent turn after a tool call, check that the Claude side executed the tool calls n8n's reply asked for (same tool, matched by name) and that the tool results it fed back equal n8n's (as the reads' effects, keyed like `compare()` keys reads); a miss fails gate 4 as `field map: tool call not executed` or `different tool result`.
- **Why not in the loop.** It changes a gate.
- **Status: applied** (approved 2026-11-15, commit e263967). `claude-side.mjs` `sameToolTurn()` per replayed agent turn after a tool call (in process): each tool n8n's reply asked for needs a Claude call of that name (names normalised as `runnerValue()` maps them) whose result is not an error, unless n8n's own result for it was empty or an error; then the reads of the turn, keyed as `compare()` keys reads, must be the same set on both sides (n8n's between the two model requests by mock-log `seq`, which recordings now keep per model call; the Claude side's between its two agent turns). A tool n8n served from a pin, or a recording without `seq`, leaves the reads unchecked (`tools.reads` says so). `gate4` checks it right after the model inputs.

## P16. The claude driver checks no model input and no tool turn

- **Evidence.** `run.mjs` `claudeDriverGates()` calls `gate4` with `modelInputs: []`, and `replay-hook.mjs` writes n8n's recorded reply for (model node, call index) into the session without comparing the request it answers, although `run.json` holds that request with the agent transcript. So a task-driver run that asks the model a different question, or whose agent tool fails, still passes gate 4 under the claude driver; P15 runs in process only. In `r2-base50` the 11 claude-driver passes follow in-process passes whose requests were checked, and both drivers use the same runner, so no verdict is known to depend on it; a step-mode runner bug (as iteration 10b found) would be missed.
- **Proposed change.** In `replay-hook.mjs`, keep each replayed request (and its time) in `replay-state.json`; in `run.mjs`, run `sameModelInput()` and `sameToolTurn()` on them for the claude driver's normal run, with the turn's reads taken from the MCP mock log and the host http log by time (both carry `t`).
- **Why not in the loop.** It changes a gate.
- **Status: applied** (approved 2026-11-15, commit c8d7237). `replay-hook.mjs` keeps each replayed request with the time its answer was written (`replay-state.json` log; a repeated write is marked and not counted); `claude-driver.mjs` returns it as `replayLog` and keeps `t` on its MCP and http effects; `claude-side.mjs` `claudeDriverModelInputs()` runs `sameModelInput()` and `sameToolTurn()` on each replayed request, a turn's reads being the effects between the previous agent turn's answer and this one's (per step and item); `run.mjs` passes them to the claude driver's `gate4` and counts them in `drivers.claude.modelChecks`.

## P17. Tool results that make no read are not compared

- **Evidence.** P15 compares a turn's results through the reads its tool calls made. A tool n8n serves from a pin or without http (a database tool with no sidecar), a Code tool or a sub-workflow tool makes no read to key, so what it fed back is never compared: in `r2-base50`, 12 of the 13 agent turns that passed the execution check had their reads unchecked (`tools.reads: unchecked …`: 2090 ×9, 4722 ×3; 2413's one turn was compared). A Code tool would compare two empty sets and pass.
- **Proposed change.** Also compare the fed-back value with n8n's tool message for the same call: parse n8n's serialisation per provider format (OpenAI and Anthropic content text, Gemini `functionResponse.response.result`), compare as JSON when both parse, else as squashed text, with run-time masking (P4); fail as `different tool result`.
- **Why not in the loop.** It changes a gate, and n8n's serialisation of tool output per tool node needs checking against the n8n 2.47.7 image first.
- **Status: applied** (approved 2026-11-15, commit c8d7237). Checked in the n8n 2.47.7 image first: a node used as a tool returns `JSON.stringify` of its output items' json, always a list (n8n-core `makeHandleToolInvocation`/`mapResult`); the Workflow tool v2 the items' json list, pretty-printed, or a string; the Code tool and the legacy HTTP Request tool their own string; `@langchain/google-genai` 2.1 sends `functionResponse.response` as `{result}` (`{error: {details}}` when the tool failed); OpenAI, Anthropic and Ollama carry the text as the tool message content. `claude-side.mjs` `sameToolValue()`: each call both sides ran without an error, JSON compared when both parse (keys sorted), else squashed text, run-time masked (P4); a list of one item equals that item, since the runtime hands the single item where n8n always sends a list (reported as `tools.shape`, not gated, P23). A miss fails gate 4 as `different tool result` with `values: [{tool, n8n, claude}]`, before the reads check; `model-shim.mjs` `normalize()` keeps Gemini's `result` and `isError`.

## P18. A model node the shim does not answer has no source at all

- **Evidence.** Writing the round-2 held-out fixtures (2026-11-15; templates not named here, since they are held out): `models` are never fixtured, but the README routes only some model types to the shim (OpenAI, Anthropic, Gemini, Ollama chat and completion, OpenRouter, legacy OpenAI). Two held-out fixtures list a LangChain LLM node whose type is not on that list as a model, with nothing to answer it: on the n8n side the call reaches the proxy unrouted, and `validate.mjs` cannot tell.
- **Proposed change.** Keep in `n8n-side.mjs` one list of the model node types the shim answers, have `validate.mjs` error on a `models` entry whose type is not on it, and route the missing LLM types whose credentials take a base URL or endpoint to the shim (the held-out fixtures' notes name them, for whoever applies this at a release point).
- **Why not in the loop.** It changes the bench's credentials and the validator.
- **Status: applied** (approved 2026-11-15, commit c8d7237). ## P19. Reads whose URL or query the model writes cannot be answered by URL

- **Evidence.** Round-2 held-out fixtures: agent search tools send a model-written query, and agent page tools and an image fetch GET a model-chosen URL. - **Proposed change.** Document the mock's answer to an unrouted read (or make it a 404 logged as `read-default`), and add an optional per-read `any: true` on a response that answers every path under its host, so a fixture can say "this site answers this page for any URL" instead of guessing.
- **Why not in the loop.** It changes the mock and the fixture schema.
- **Status: applied** (approved 2026-11-15, commit c8d7237). `mock-server.mjs`: with bench routes, a read no route matches is 404 `{"error":"no fixture"}` logged `read-default` (the in-process host records the same, the claude driver's host mock is the same code); `logVsFixture.unanswered` lists them. `any: true` on a read's response (schema, `routesOf`, `pickRoute`) answers every path on the url's origin, only for requests that name an origin; an exact-path response always wins over it; `routeKey` carries ` any`. `validate.mjs` errors on `any` in `writeReplies`.
